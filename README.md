# 智能座舱 Agent

这是一个可运行的 Python 教学项目，提供命令行和本地网页，演示 **规则／本地向量 NLU → Planner全局规划 → ReAct单任务执行 → Replanner修订 → Responder自然回答**。车辆、耗电和原机场案例是模拟数据；高德导航可查询真实地点、驾车路线、地图概览与路书，无真实车辆控制。

项目有两条路径：明确的简单命令由本地规则或语义NLU处理；复杂出行咨询交给支持工具调用的真实模型。另附不需要密钥的固定离线案例，方便先读懂流程。原有命令默认 `--nlu rules`；新增的本地向量版本见下文。

## 最终回答：先回答问题，再保留执行明细

live模式采用 **Planner → Executor/ReAct ↔ Replanner → Responder**。Planner提交初始业务目标图，Executor记录真实成败，Replanner可修订剩余目标；新增`cockpit/responder.py`再调用一次未绑定工具的聊天模型，根据原问题与实际回执综合回答。它可以比较方案、解释推荐理由、自然地说明部分任务为何未完成，而非把任务ID、工具名和JSON逐条发给用户。

例如问“电量只有25%，去机场要不要充电？帮我比较方案，给个建议”，回答应先说明模拟节能路线可不充电的依据，再比较高速与充电备选。行驶中混合车控则应说清楚“空调已设置，但灯和座椅未操作，原因是行驶限制”。网页任务明细默认折叠，参数、依赖、权限、成败和原始结果仍能展开查看。

- 整理器仅能读取结果，没有工具或执行服务引用；即使输出工具调用也不执行。完整任务记录与最终文案分开保存，会话历史保留真实回执。
- 不展示模型内部思考；输入压缩省略地图几何/路书大字段，保留关键查询数值、错误及事实摘要。
- 有限检查会拒绝空文案、JSON/工具日志、明显误报全部成功、证据外的新阿拉伯数值，以及遗漏默认续航假设或把规划说成已到达等情况。检查不能完整理解自然语言，也不能保证所有推荐或措辞正确；保守检查可能拒绝合理的数字换算，仍需真实任务评测。
- 整理请求超时、服务异常或检查失败时，按真实记录生成中文兜底，明确提示整理不可用。已经完成的任务不回滚、不重试，也不会误报“本轮尚未执行”。
- 本地单意图NLU、offline固定案例及需要澄清的请求仍直接回答，不增加模型调用。live轮次包含初始规划、逐任务ReAct、必要的重规划及回答整理，会增加延迟和调用成本；每次模型网络超时为20秒，不是整轮总时限。

事件新增`response.started/completed/fallback`。执行记录的`answer.source`区分`model`和`fallback`，便于确认展示的文案来源。真实验证可显式运行`.venv\Scripts\python.exe tests/smoke_answer.py`；续航真实模型用例`tests/smoke_range.py`也会检查回答已通过整理。

## 剩余续航工具与长期行驶记忆

现在可以直接问 **`当前电量还能跑多远`**、`估算剩余续航` 或 `查看历史行驶记录`。这些完整规则表达在offline/live中都走本地工具，不需要模型密钥。复杂表达和多意图会交给Planner，模型可选择两个只读工具：

- `estimate_driving_range()`：读取当前会话模拟SOC、本车长期保存的可用电池容量、历史能耗，重新计算剩余公里数。
- `get_driving_history(limit=10)`：查询本车人工行程记忆及统计，limit只允许1～20。

向量NLU仍只有原有温度与车辆状态示例，没有增加第三类或重新校准；未命中规则的续航/历史表达增加专用拒识边界，避免被误当普通车辆状态查询。

### 网页演示

```powershell
.\.venv\Scripts\python.exe web.py --mode offline --nlu rules
```

打开 <http://127.0.0.1:8765>，右侧新增“续航与行驶记忆”面板。展开“设置电量与录入行程”：

1. 当前模拟电量填`25`、可用电池容量填`60`，点击“保存电量与容量”。容量必须按本车可用容量填写；初始60kWh仅为教学假设，不是厂家参数。
2. 填入**已完成**行程里程`50`km、实际耗电`8.5`kWh，点击“保存行程到长期记忆”。这只是虚构演示样例，页面不会自动添加样本。
3. 输入`当前电量还能跑多远`：按17kWh/100km计算，保留10%电量约52.9公里，理论耗尽约88.2公里。界面与回答注明样本数量、来源和适用边界。
4. 再录入另一条行程，查询会重新读取数据库计算。刷新页面、重启服务或重置聊天后，已保存记录及容量仍保留；模拟SOC重置为25%。

容量与行驶记录默认属于单辆教学车`demo_vehicle`，**所有本机浏览器会话和CLI共享同车记忆**；当前模拟电量仍按会话独立。存储层支持不同vehicle_id隔离，但前端未实现车辆切换、用户身份认证或多租户授权，不要把浏览器会话隔离误认为长期记忆的用户权限隔离。

### 计算与存储

```text
历史百公里能耗 = 最近最多100条本车记录的总耗电(kWh) / 总里程(km) × 100
保留预留电量可行驶距离(km)
  = 可用电池容量(kWh) × max(当前电量% − 预留电量%, 0) / 历史百公里能耗(kWh/100km)
理论耗尽距离(km) = 可用电池容量(kWh) × 当前电量% / 历史百公里能耗(kWh/100km)
```

这里使用百分数数值25、10，所以公式不再额外乘100。例如60×(25−10)/17≈52.9。按总里程加权，避免短途和长途被赋予相同权重。历史记录不删除，仅最近录入的100条参与本轮统计；时间戳表示录入时刻，不代表真实行程发生时间。未使用向量数据库、对话摘要、LLM记忆或模型微调。

无历史时明确采用`18kWh/100km`教学默认能耗；少于3条时提示样本不足。低于或等于10%预留时，可用距离为0，不输出负数。结果尚未建模气温、坡度、车速、载重、驾驶风格、电池衰减或电量估计误差，不能视为实测续航或可达性保证；也没有把高德真实路线转成可信的能耗/到达电量预测。

SQLite默认位置为`runtime/driving_memory.sqlite3`，无额外依赖，数据文件及journal/wal/shm已加入Git忽略。可通过CLI/Web的`--memory-db 路径`指定独立演示文件。每次读写使用短连接事务；行程有车辆ID和UUID唯一约束，同一次保存超时后重试不会重复计入。不同的新UUID即视为新行程，不能识别用户手动重复录入的同一真实行程。

本版接受1～2000km、0.001～300kWh，且百公里耗电3～60kWh的净耗电行程；拒绝NaN、无穷、布尔值、非正耗电及超出范围的样本。是否混入充电、单位是否填错仍需录入者核对，无法仅凭这两个数值完全识别。这是教学数据校验范围，并非所有车型的物理边界。数据库不可用时明确报错，不把读取失败当成“无历史”。

行程录入和容量修改只通过显式面板/CLI入口，模型没有写入长期记忆的工具，也不能覆盖续航工具的SOC、车辆ID或电池容量参数。只读工具本地计算不联网；live请求、历史工具结果和最近上下文仍可能发送到已配置的模型服务。本机数据库未加密，不保存路线坐标；请使用教学数据。

## 分层任务执行：Planner + ReAct + Replanner

运行方式不变，没有新增依赖：

```powershell
.\.venv\Scripts\python.exe web.py --mode live --nlu rules
.\.venv\Scripts\python.exe main.py --mode live --nlu rules
```

NLU仍先识别明确单意图并本地执行；进入Agent的所有任务（含车控）都走单任务ReAct。offline保留原NLU与固定机场脚本，不把固定脚本称为模型规划。没有新增LangGraph、后台任务、实时插话或取消接口；同会话执行期间仍拒绝并发请求。

```text
Planner提交业务目标DAG → Executor调度就绪目标 → TaskWorker(ReAct)
                                               ↓ 动态工具 → 真实观察 → 决定下一步
                      目标完成 ← finish_task引用成功回执
                      可恢复异常 → 暂停新任务、等待在途返回
                                    ↓
                              Replanner修订剩余图 → 新版本校验 → 继续调度
最终有效目标与恢复记录 → Responder自然回答（失败则事实兜底）
```

### 业务任务图

全局任务不再等同一次工具调用。任务字段为`id/kind/goal/inputs/depends_on/condition`，不接受旧的`tool/arguments`任务格式：

```json
{"tasks":[
  {"id":"temp","kind":"vehicle_control","goal":"将空调设为24度","inputs":{"tool":"set_temperature","arguments":{"temperature":24}},"depends_on":[],"condition":null},
  {"id":"trip","kind":"airport_advice","goal":"分析机场路线与充电备选","inputs":{"view":"advice","destination":"机场"},"depends_on":[],"condition":null},
  {"id":"state","kind":"vehicle_state","goal":"查询设置后的车辆状态","inputs":{},"depends_on":["temp"],"condition":null}
],"clarification":""}
```

`kind`固定为车辆控制、车辆状态、剩余续航、行驶历史、导航、模拟机场建议六类。应用按类别分配工具范围，模型不能通过`allowed_tools`等字段提权。导航又区分目的地自动导航、明确起终点及只搜索地点；只搜索地点的目标没有修改导航计划的权限。

一个机场建议目标内部可先查车辆状态，再查路线，根据到达电量决定是否查充电站；这些调用由ReAct观察后决定，不是Planner预先写死的工具列表。导航起终点坐标必须来自本任务或前置任务真实查询，不能由模型编造。

前置结果继续用`{"$ref":"routes.data.routes.0.route_id"}`引用；`data`是该目标的主要工具真实data，不是模型自由生成的摘要。`condition`继续支持`eq/ne/lt/lte/gt/gte`单条件。完整图先校验ID、输入字段、引用、依赖和无环性，再执行。

### 单任务ReAct与完成证据

每次模型决策只允许一个调用，观察后再选择下一步；多个独立业务目标仍最多4线程调度。同一执行器和导航计划增加资源顺序约束，车控检查/写入/读回继续共用状态锁。

模型通过`finish_task(primary_step_id, evidence_ids)`结束目标。所有ID必须指向本任务实际成功步骤，主要回执必须符合目标类别：车控必须是目标写入且已核验，续航必须调用续航工具，导航必须有实际路线，机场建议至少查询本轮状态和路线。没有证据的成功声明无效。起点与目的地过近、需要核对入口时明确要求澄清，不把“检测到附近”当成已规划或已到达。

工具步骤保存在`steps`中，`called=false`区分被范围/参数/证据检查拒绝的提议；`attempts`仅计实际调用。只展示动作、观察和简短决策事件，不记录模型内部思考。

### Replanner与跨轮需求修改

出现可恢复失败后停止提交新目标，等已开始的目标返回，再冻结成功任务。Replanner提交剩余目标和`replacements={旧ID:新ID}`；代码检查：

- 成功事实不能覆盖或重放，替代目标使用新执行ID，旧失败及其回执保留在审计中。
- 原任务的类别、目标、输入和条件不能放宽；只允许更新替代任务引用并补充前置依赖，不能删除原有业务依赖。
- 可补充状态、续航或历史等只读前置，不可凭空新增车控或改目的地。每个版本重新校验全图与资源顺序。
- 修订无效、目标仍无法满足或预算用完时结束修订，保留实际结果；无关任务继续，失败依赖的后继跳过。

下一轮进入Agent时，Replanner读取上轮事实，判断是独立新请求还是目标修改。例如第一轮`空调调到24度，并导航到北京南站`，第二轮`改去北京西站，刚才空调不动`，只生成新导航/必要查询，不重放空调。已经完成的操作不自动撤销。分类器附带的多余新请求草案被忽略；需求修订格式不合法时只回到一次完整Planner，绝不执行坏图。

当前是轮次间修改，不支持用户在HTTP请求尚未结束时插话、修改或取消。RunState只保存在进程内；reset清空运行状态和对话，但不删除SQLite行驶记忆，也不提供重启后任务恢复。

### 授权、异常与预算

原句写授权在整轮创建一次，线程安全地按工具和精确参数消费，跨ReAct及所有计划版本保留。历史命令、模型声明和高相似度不产生授权。每次实际车控仍经过Safety Guard，停车不会重新授予已经消费的权限。

安全拦截、无授权、缺配置/服务权限、记忆库不可用、写入未知或读回失败不自动重试相关写入。若写入已真实核验，随后模型超时或未正常收束，则由代码保留成功回执完成目标，不重复操作。查询网络错误仅额外重试一次，按整轮相同查询统一计数，不叠加ReAct与Replanner的重试。

默认上限：12个有效目标、4个并行Worker、每任务6次模型决策、每轮2次重规划、累计24个任务实例及40次模型请求。调度预算120秒，在每次新调用前检查；单次模型网络超时仍20秒。不会强杀线程或声称预算到达即可撤销在途调用，已开始调用等实际返回。Responder也计入模型请求次数，预算不足时使用事实兜底。

## 车辆安全判别：行驶限制与停车放行

按本项目的教学策略，新增前照灯、座椅和雨刮模拟控制。安全判断由 `cockpit/safety.py` 的确定性代码执行，放在共享 `ToolService` 内部；不依赖模型是否记住提示词。以下是本项目的演示策略，不是适用于所有车型的操作规范或法规：

| 动作 | 0km/h＋P挡＋已驻车 | 行驶/未驻车/状态未知 |
| --- | --- | --- |
| 打开、关闭前照灯 | 通过安全检查 | 拦截 |
| 调整座椅位置 | 通过安全检查 | 拦截 |
| 关闭雨刮器 | 通过安全检查 | 拦截 |
| 开启雨刮器、调整低速/高速 | 通过安全检查 | 通过安全检查 |
| 查询状态、原有空调设置 | 通过安全检查 | 通过安全检查 |

“通过安全检查”不等于取得写权限。明确完整的本地NLU命令由应用传入 `allow_write=True`；多意图Executor按本轮原句逐任务授权，停车不会自动提权。执行层先检查动作的状态安全条件，再检查写授权。Agent即使被提示词诱导提交这些任务，行驶时也返回 `SAFETY_BLOCKED`，停车但没有原句授权时返回 `WRITE_NOT_AUTHORIZED`。

### 安全模块与执行流程


### 与Agent、离线模式的关系

网页导航面板是**独立的显式联网入口**：点击搜索、规划、加载地图会将地点/坐标发送给高德，无需LLM，也不受聊天的offline/live开关影响。普通offline聊天和原机场固定脚本仍不调用高德，原有NLU断网测试继续成立。

在live聊天中，Agent使用以下导航相关工具：

- `search_navigation_places(keywords, city)`：搜索真实地点，返回名称、地址、ID及GCJ-02坐标；有歧义时应让用户选择。
- `plan_navigation_route(origin, destination, strategy)`：起终点各为 `{name, location, id?}`，不含搜索结果中的address；返回真实驾车路线和高德链接，不启动导航。
- `get_vehicle_location()`：读取已设置的模拟车辆位置，返回来源与坐标系；未设置则报错。
- `navigate_to_destination(destination, strategy)`：自动从当前模拟车辆位置出发，按代码中的匹配和距离排序策略选择目的地并规划。

可输入：“查询从北京南站到首都机场T3的真实驾车路线，城市是北京；有同名地点先让我选择。”该显式起终点流程保留人工选择规则；只给目的地的指令则走上面的自动就近流程。模型对语言和路线偏好的提取仍可能出错，日志保留实际工具参数和结果便于核对。

三个联网高德工具返回 `simulated=false`，自动导航结果另标明 `origin_simulated=true`；`get_vehicle_location`、原 `get_route_options` 和 `find_chargers` 返回 `simulated=true`。不能把原来的18%/12%耗电套到真实高德路线。模型不能自行授予写权限、点击浏览器按钮或启动高德App。

工具日志包含查询地点、坐标和路线；live Agent的工具结果及最近上下文可能发送给配置的模型服务。本版本没有位置脱敏网关，演示建议使用公开地点。导航状态只保存在进程内当前浏览器会话，重置会清空路线并使旧地图ID失效。

### 匹配原理与执行边界

```text
规则完整命中 → 写操作检查 → 共享工具
未命中 → 本地边界检查／缺槽位澄清
       → 温度数字替换成<温度>
       → BGE编码并归一化
       → 与32条示例向量做点积
       → 每个意图取最高分
       → 检查最高分和两个不同意图的分差
       → 温度命令再检查表达、槽位和权限
       → 本地执行／澄清／回到原Agent或离线分支
```

本地向量补充仍支持两个意图：`set_temperature` 和 `query_vehicle`；新增前照灯、座椅、雨刮由独立的完整规则识别，不使用这两类向量分数授权。温度支持一个绝对目标及中文数字，例如二十四、二十四点五；“再低两度”只提示澄清，尚不维护相对调节槽位。

相似度不是概率。负面、假设、引述、疑问、多指令、延后执行、明确其他设备或未支持车辆部件，都有保守检查。规则和语义路径都不能靠高分绕过写检查；多意图Agent路径也必须取得应用侧逐任务授权。这里是有限规则集，不是能理解所有语义的安全分类器，也不保证能阻止所有自然语言攻击。

`NLU识别`日志会显示来源、候选意图、参数、相似度、不同意图分差、最高分示例、拒识原因和识别耗时。`nlu_guard`表示确定性检查；`semantic_nlu`表示使用了本地向量；规则直接匹配不会计算查询向量。

### 修改示例和校准

数据保存在 `nlu_data/`：

| 文件 | 用途 |
| --- | --- |
| `examples.json` | 2个意图各16条示例；不训练权重，只建立内存向量矩阵 |

校准遍历similarity与margin阈值，优先最少误接受，再最多正确本地接受，最后取更严格阈值。similarity为1.01代表关闭该意图的语义接受。当前校准结果：温度 `0.85 / 0.10`，车辆查询 `0.74 / 0.04`。

校准和测试的分组ID与文本不交叉，也检查温度脱敏后的模板不重复；明确标记的数值边界回归案例允许重复规则模板。文本由人工编写，样本量很小、表达可能相近，不能据此宣称真实用户分布下的准确率。

## 3. 先理解这张流程图

```text
用户文字
   ↓
app.handle：先调用规则NLU（hybrid另有本地向量补充）
   ├─ 完整命中 → 共享工具层校验 → 操作/查询 → 结果反馈
   └─ 拒识、需澄清或多个意图
       ├─ offline → 仅匹配预置出行案例 → 固定顺序调用工具
       └─ live → LLM Planner提交一次任务图
                   ↓ 完整结构校验、白名单、无环性
                 Executor：依赖就绪／条件／结果引用／最多4个ReAct任务并发
                   ↓ 每个车控任务检查原句授权＋Safety Guard
                 工具真实回执 → ReAct完成证据／Replanner修订 → 只读Responder组织回答
                                             └─ 整理失败 → 中文事实兜底
```

**离线出行案例是固定脚本，不能证明模型具备自主规划能力。** 在 `app.py` 的 `_offline_trip` 中，工具顺序由代码写死；真实模式中Planner提出业务目标图，TaskWorker根据观察动态调用工具，Replanner受约束地调整剩余图。LangChain提供模型、消息、工具Schema及结构化调用适配，没有额外引入LangGraph。

### 一次完整的机场查询

本地假设：当前25%电量，到达至少预留10%。

| 方案 | 时间 | 预计到达电量 | 判断 |
| --- | --- | --- | --- |
| 机场高速 | 48分钟 | 25−18＝7% | 低于预留 |
| 机场节能路线 | 65分钟 | 25−12＝13% | 满足预留 |
| 高速＋服务区充电 | 48＋8绕路＋20充电＝76分钟 | 25＋30−18＝37% | 模拟可选备选 |

充电站C01有2个可用端口；节能路线的C02端口为0，应排除。这里的充电时间和恢复电量均为固定教学假设，忽略抵达充电站前的分段耗电与充电曲线，不能用作现实出行或充电建议。没有时限要求时，预设案例选择无需充电的节能路线。

工具查询不改变电量，不会真的导航、预约或充电。日志示意：

```text
[路由] path=planner_executor
[规划完成] state / routes / chargers，以及依赖/条件
[任务状态] state running → succeeded，battery_percent=25
[任务状态] routes running → succeeded，两条模拟路线
[任务状态] chargers按真实电量条件执行 → succeeded
助手：逐项汇总查询时的电量、路线到达电量和充电备选。
```

调试日志输出结构化JSON，便于核对。聊天正文由Responder直接回答原问题，任务明细另行展示；不会打印模型内部推理内容。规划和回答仍可能出错，应区分规划正确性、执行真实性和最终表达质量；当前输出检查只覆盖有限模式。

### 关键接口

- `parse_intent(text) -> Intent | None`：返回意图、工具名与参数，未覆盖的表达返回 `None`，没有训练模型或置信度分数。
- `ToolService.execute(name, arguments, allow_write=False) -> dict`：统一入口，返回 `ok`、`simulated` 和 `data` 或 `error`。
- `get_vehicle_state()`：读取电量、温度和预留阈值。
- `set_temperature(temperature)`：校验16～30℃，明确本地指令或取得原句逐任务授权才可写。
- `get_route_options(destination)`：只接受“机场”，计算两条路线的到达电量。
- `find_chargers(route_id="")`：支持 `airport_fast`、`airport_eco`，空字符串查询全部站点。
- `Planner.plan(text, history) -> TaskPlan`：一次模型调用并校验任务图；不执行业务工具。
- `Executor.execute(plan, user_text)`：执行DAG并返回逐任务真实记录；共享工具层再次校验参数、安全与权限。
- `LiveAgent.run(text, history)`：串联Planner、ReAct、Replanner和Responder，返回自然回答及附真实回执的本轮普通消息对。

### 为什么复杂请求还要逐任务授权？

LLM提出某项动作不等于用户授权。本地单意图NLU仍保留明确表达和槽位检查；多意图Executor只为本轮原句中规则可验证、参数一致的明确写命令传入`allow_write=True`。例如`查路线并把空调调到24度`可授权24℃这个子任务；`不要把空调调到24度`即使被误规划成写任务也会拦截。历史命令不能为本轮重复动作授权。

这是一个可验证的最小权限示例，不是完备的用户授权系统。传给模型的工具参数里没有 `allow_write`，模型不能通过参数自行提权。

### 当前 Harness 做了什么？

Harness 是围绕模型的运行支撑代码。本项目包含工具定义、结构化参数、共享执行校验、状态读回、进程内上下文、日志、错误提示，以及以下边界：

- 单次网络请求超时20秒，关闭 SDK 自动重试；这不是整轮任务的总超时。
- 每轮最多12个有效目标、4个Worker、每目标6次决策和2次重规划；累计24个实例、40次模型请求。120秒调度预算停止新调用，不强制取消在途调用。
- 最多保留最近10个完整对话轮次，不按 token 精确计量；工具结果过长仍可能超上下文。
- 工具失败进入逐任务状态，正常轮次保存真实执行摘要。规划失败保留用户请求与失败说明，不将未闭合的工具调用消息带入下一轮。
- reset 清空调用方传入的历史；本版本没有独立的持久化 checkpointer。

尚未实现：ASR/TTS、训练式NLU、真实车控与车载定位导航SDK、权限确认流程、持久化恢复、持久化幂等操作账本、执行中任务取消、多Agent、隐私网关及生产级评测。真实地图路线接入见上文高德导航章节。

## 5. 五分钟面试演示与答法

**第1分钟：定位。** “这是一个规则NLU与LLM工具调用协同的座舱教学原型。简单指令本地处理，复杂咨询交给模型，执行校验由统一工具层负责。”

**第2分钟：车控。** 输入“空调调到24度”，指出意图是设置温度、槽位是24；输入“空调调到35度”，展示工具拒绝写入。

**第3分钟：多意图。** live输入“把空调调到24度，并打开前照灯，然后查询车辆状态”，展示两个独立任务与依赖查询。没有密钥时只展示固定计划接线测试或离线脚本，说明演示边界。

**第4分钟：安全和失败。** 切到模拟行驶，输入“关闭前照灯，并座椅调到60%，同时空调调到23度”，展示拦截与独立任务继续。说明依赖失败会跳过后继，不会回滚已成功任务。

**第5分钟：验证与改进。** 展示测试结果和能力边界，说明下一步会补语音、真实服务、持续评测和可恢复任务。

| 面试问题 | 可以怎样回答 |
| --- | --- |
| NLU与Agent有什么区别？ | NLU处理覆盖范围内的单意图与槽位；Planner把复杂目标拆成带依赖的任务图，Executor依据真实结果调度。 |
| 为什么不全用LLM？ | 明确高频指令可以本地执行，减少模型调用依赖；但延迟、准确率和成本收益需要实测，这个版本没有做效果对比实验。 |
| 为什么用LangChain？ | 复用模型适配、消息和工具Schema；任务DAG调度由本项目Executor实现，便于学习并行、依赖与安全边界，没有另加LangGraph。 |
| Agent自主性在哪里？ | 模型选择任务、参数、依赖和条件；运行时按工具真实结果决定能否执行后继。ReAct根据观察动态调用，Replanner可在预算内修订剩余目标。 |
| 怎样减少幻觉？ | 模型不直接执行；计划先校验、参数可引用真实观察值。回答模型只读真实结果，进行有限数字/状态模式检查并保留事实兜底；仍须评测规划与回答质量，不能保证消除幻觉。 |
| 工具报成功就够了吗？ | 温度设置后读回实际内存状态核验；真实设备还需要回执、超时和状态查询。 |
| 超时后能恢复任务吗？ | 这里只提示失败并允许发起新请求，没有断点恢复；下一步才考虑持久化状态、幂等和副作用对账。 |
| 项目做了隐私保护吗？ | 密钥不进正常日志，offline不调用模型；live会发送上下文，没有实现端云脱敏，不能声称隐私数据不出端。 |
| 怎样评测？ | 本版测试确定性规则、参数与写权限、数据一致性、上下文和失败行为；后续需要独立任务集、真实模型成功率、延迟及成本评测。 |
